% ------------------------------------------------------------------ Abstract
\begin{abstract}
This study asks how loop reordering and cache blocking change the runtime of sequential float64 dense
matrix multiplication, and at which densities a compressed sparse row (CSR) representation with Gustavson's
sparse--sparse product (SpGEMM) beats a dense kernel. All methods are my own C code (gcc~13.3 \texttt{-O2}, one thread) on an
Intel i7-9750H laptop, validated against NumPy/SciPy and timed with 1 warm-up and $k=5$ repetitions (median
and interquartile range) under a 600\,s and 8\,GiB per-process budget. Relative to the naive i-j-k loop,
reordering (i-k-j) was \val{SpMinIkj}--\val{SpMaxIkj}$\times$ faster and reordering plus blocking
\val{SpMinBlk}--\val{SpMaxBlk}$\times$ faster (95\,\% confidence interval at $n=3072$: [\val{SpLoBlkThreeZeroSevenTwo},
\val{SpHiBlkThreeZeroSevenTwo}]); only the optimised kernels completed $n=4096$ within budget. At $n=2048$,
SpGEMM was faster than the dense kernel up to 50\,\% density and slower from 70\,\%, for uniform and banded
nonzeros, a crossover near 55\,\% that a per-operation cost model reproduces. Conversions dominate at low
density, and at equal density the uniform pattern produced up to \val{NnzCUoverBDtwo}$\times$ more output
nonzeros and ran up to \val{UoverBDtwo}$\times$ slower than the banded one. The conclusions are limited to this
machine, compiler and the synthetic inputs tested.
\end{abstract}

% ------------------------------------------------------------------ Introduction
\section{Introduction and Objective}
\label{sec:intro}
Matrix multiplication is a building block of data-intensive computing (linear models, graph analytics,
recommendation, neural networks). The classical algorithm performs $2n^3$ floating-point operations
for two $n\times n$ matrices, but how fast those operations run depends far more on how the data move
through the memory hierarchy than on the operation count itself~\cite{hennessy2017,goto2008}. When most
entries are zero, a sparse representation can avoid both the storage and the arithmetic of the zeros, at
the price of index arithmetic, irregular memory access and an output whose sparsity is not known in
advance~\cite{gustavson1978,buluc2012}.

This study addresses two research questions (RQ) on a single laptop core:
\begin{itemize}
\item \textbf{RQ-A.} How much do loop reordering and cache blocking reduce the runtime of float64 dense
  multiplication relative to a validated naive baseline, and how does the effect change with $n$?
\item \textbf{RQ-B.} For matched logical inputs, at which tested densities does a compressed sparse row
  (CSR) representation with Gustavson's sparse--sparse product (SpGEMM) run faster or use less memory
  than the best dense kernel, and how does the answer depend on the nonzero structure and on the
  conversion costs?
\end{itemize}
Throughout, \emph{density} $d$ is the percentage of nonzero entries and \emph{sparsity} $1-d$ the
percentage of zero entries. The hypotheses below were written before the full benchmark
(\texttt{docs/experiment\_plan.md}); they are predictions, not results:
\begin{itemize}
\item \textbf{H1.} Both optimised kernels are faster than the naive i-j-k baseline, with a gap that grows
  with $n$.
\item \textbf{H2.} Blocking adds a benefit over plain reordering once the three matrices exceed the
  \SI{12}{MiB} last-level cache ($n\gtrsim 1024$).
\item \textbf{H3.} SpGEMM beats the dense kernel below a crossover density that depends on the nonzero
  pattern; since SpGEMM work grows like $d^2n^3$ for uniform inputs, the crossover is expected at a
  relatively high density.
\item \textbf{H4.} Output fill-in and conversion costs reduce the sparse advantage as $d$ grows; at equal
  density, a banded pattern is faster than a uniform one.
\end{itemize}
The comparison is sequential (one thread) and in C for every method. Assignment~1 did not yet provide a
validated C kernel when this work started, so an equivalent naive baseline was implemented and validated
here (\cref{sec:impl}). Assignment~1 has since added a C kernel with the same i-j-k loop, scalar
accumulator and compiler flags (repository \texttt{bigdata-assignment01-matmul-languages}, commit
\texttt{dfb18bf}); the baseline of this study remains the one validated here.

% ------------------------------------------------------------------ Background
\section{Background and Related Work}
\label{sec:background}
\textbf{Dense kernels and the memory hierarchy.} In the i-j-k order each output $C_{ij}$ is a dot product of
row $i$ of $A$ and column $j$ of $B$; with row-major storage, consecutive iterations of the inner loop read
$B$ with a stride of $8n$ bytes, so almost every access to $B$ touches a different cache line once $B$ no
longer fits in cache~\cite{hennessy2017}. Interchanging the two inner loops (i-k-j) turns the inner loop into
an update $C_{i,:} \mathrel{+}= a_{ik}B_{k,:}$ with unit stride on $B$ and $C$, the same arithmetic in a
different order. Such a loop is a candidate for SIMD vectorisation, which gcc enables at \texttt{-O2} since
version~12, but only under a ``very-cheap'' cost model~\cite{gcc12}; for the kernels of this study it does
not apply (\cref{sec:impl}). Cache blocking (tiling) partitions the iteration space into $b\times b$ tiles so
that the working set of a tile update ($\approx 3\cdot 8b^2$ bytes) is reused while it stays in cache; Lam
et al.\ showed that the benefit depends strongly on the block size and on cache interference~\cite{lam1991}.
High-performance libraries combine blocking for every cache level with packing and register-level
micro-kernels~\cite{goto2008}; this study implements only the first ingredient. The roofline model relates
attainable performance to arithmetic intensity and memory bandwidth~\cite{williams2009} and is used here
only qualitatively. Strassen's algorithm~\cite{strassen1969} reduces the operation count to
$O(n^{2.81})$ but was not implemented (see \cref{sec:limits}).

\textbf{Sparse storage and SpGEMM.} CSR stores, for each row, the column indices and values of its nonzeros
plus a row-pointer array~\cite{saad2003}. Gustavson's algorithm~\cite{gustavson1978} computes $C=AB$ row by
row: for every nonzero $a_{ik}$ of row $i$ it scatters $a_{ik}B_{k,:}$ into an accumulator and finally
gathers the touched columns. Its work is proportional to the number of scalar multiply-adds
$\mathrm{flops}=\sum_{a_{ik}\neq 0}\mathrm{nnz}(B_{k,:})$ plus $O(n+\mathrm{nnz}(C))$, which for uniform
random inputs is about $d^2n^3$, i.e.\ a factor $d^2$ of the dense work. The output can be much denser than
the inputs, and its structure is only known after a symbolic phase~\cite{buluc2012}. For two independent
uniform inputs, $P(C_{ij}\neq 0)\approx 1-(1-d^2)^n$, so at $n=2048$ the product is almost full once
$d\gtrsim 5\%$.

\textbf{Benchmarking.} The protocol follows common recommendations: report medians with a dispersion
statistic over repeated runs, state the timing boundary and the environment, and treat measurements as
sensitive to seemingly irrelevant setup details~\cite{hoefler2015,mytkowicz2009}.

\section{Methodology}
\label{sec:method}

\subsection{Implementations}
\label{sec:impl}
All kernels are my own C11 code, compiled with gcc~13.3 \texttt{-O2 -std=c11} (identical flags, no
\texttt{-march=native}, no BLAS, one thread), operate on float64 row-major arrays, and share the interface
of \texttt{src/c/dense/matmul\_dense.h}:
\begin{itemize}
\item \texttt{naive\_ijk} (baseline): i-j-k triple loop with a scalar accumulator per $C_{ij}$.
\item \texttt{reorder\_ikj} (optimisation 1, loop reordering): i-k-j order, $C$ zeroed first; the only change
  is the loop order, which gives unit stride on $B$ and $C$ and keeps $a_{ik}$ in a register.
\item \texttt{blocked\_ikj}($b$) (optimisation 2, cache blocking): the i, k and j loops are tiled into
  $b\times b$ tiles (edge tiles smaller) with i-k-j inside each tile. The block size is chosen by the study
  in \cref{sec:res-blocks}.
\item \texttt{csr\_gustavson}: own CSR (\texttt{int64} row pointers, \texttt{int32} column indices,
  \texttt{float64} values; $12\,\mathrm{nnz}+8(n+1)$ bytes) and own two-phase Gustavson SpGEMM. A symbolic
  pass counts the distinct columns of every output row with a marker array so that $C$ is allocated
  exactly; a numeric pass accumulates into a dense accumulator of length $n$ and gathers the touched
  columns. Output columns are left unsorted; structural nonzeros are kept even if a sum cancels.
\item Conversions \texttt{dense$\to$CSR} (two passes: count, fill) and \texttt{CSR$\to$dense} (scatter).
\end{itemize}
The generated assembly (\texttt{gcc -S}) and the vectoriser report (\texttt{-fopt-info-vec-all}) show that
none of the three dense kernels is vectorised at \texttt{-O2}: all use scalar \texttt{mulsd}/\texttt{addsd}
instructions (no FMA). The dense comparison therefore isolates the effect of the memory-access order; it
does not include any SIMD effect.
NumPy~\cite{harris2020} and SciPy~\cite{virtanen2020} are used only to generate inputs and as correctness
references; no library code is inside any timed region.

\subsection{Inputs}
Dense inputs are $n\times n$ float64 matrices with entries $\sim U[-1,1)$ drawn with NumPy's PCG64 generator
(\texttt{default\_rng}, $A$ seed 42, $B$ seed 43). Sparse inputs have exactly $\mathrm{nnz}=\mathrm{round}(dn^2)$
distinct positions with values $\sim U[-1,1)$ (exact zeros redrawn, so every stored entry is nonzero). Two
nonzero patterns are used: \emph{uniform} (positions uniform over the matrix) and \emph{banded} (positions
uniform inside the narrowest band $|i-j|\le w$ that can hold nnz entries). Seeds are $1000+10^6d$ for $A$ and
that value $+1$ for $B$. Every input is written once to \texttt{data/inputs/} (raw float64, or coordinate-format (COO) triplets) with
a JSON sidecar (generator, seed, nnz, band width) and a SHA-256 checksum, and is read by every method, so all
methods see byte-identical inputs. The tested densities at $n=\val{SpN}$ are
$d\in\{0.1,0.5,1,2,5,10,20,30,50,70,100\}\%$; the sparse scaling study uses $d\in\{0.1,1\}\%$ and
$n\in\{1024,\ldots,16384\}$, plus $n=32768$ at $d=0.1\%$.

\subsection{Correctness validation}
\texttt{tests/test\_correctness.py} runs the compiled programs and must pass before any benchmark. Dense
kernels (and blocked with $b\in\{1,3,16,64,256\}$, including sizes not divisible by $b$) are checked on known
$2\times2$ and $3\times3$ products, identity and zero matrices (exact equality), and random matrices with
$n\le 257$ against NumPy. Sparse modes are checked against SciPy on identity, zero, empty rows/columns, a
known $2\times2$ case and generated uniform and banded inputs; nnz$(C)$ must equal the structural nonzero
count, and the reported flop count must match an independent count. The floating-point tolerance is the
componentwise bound of the classical algorithm evaluated in any order~\cite{higham2002},
$|C-C_{\mathrm{ref}}|_{ij}\le 2nu(|A||B|)_{ij}$ with $u=2^{-53}$ (the factor 2 covers both evaluation
orders). All checks passed; over the \val{CorrChecks} tolerance comparisons the largest error was
$\val{CorrMaxAbs}$, at most \val{CorrMaxRatio} of the bound.

\subsection{Measurement protocol and budgets}
\label{sec:protocol}
\textbf{Timing boundaries.} Time is measured with \texttt{clock\_gettime(CLOCK\_MONOTONIC)} around one kernel
call; loading inputs and allocating and zeroing $C$ happen before the timer, and a checksum of $C$ is printed
afterwards so that the computation cannot be removed. The boundaries are never mixed in one comparison:
\texttt{kernel} (Part~A); \texttt{spgemm\_kernel} (CSR$\times$CSR$\to$CSR including the symbolic phase and the
allocation of $C$; inputs already in CSR); \texttt{dense\_kernel} (blocked kernel on the densified sparse
inputs); and the conversions \texttt{dense$\to$CSR} (both inputs) and \texttt{CSR$\to$dense} (output), measured
separately in their own process. ``SpGEMM including conversions'' is the explicit sum
dense$\to$CSR + SpGEMM + CSR$\to$dense.

\textbf{Repetitions and statistics.} One process per configuration runs 1 warm-up and $k=5$ measured
repetitions; for the costly dense sizes $n\ge 3072$ there is no warm-up and $k=3$ (declared in advance for the
time budget). Warm-ups are excluded; no other rows are excluded. I report the median and the interquartile
range (IQR); throughput is reported in GFLOP/s ($2n^3$ floating-point operations divided by
the median time, in units of $10^9$ per second); speedups are ratios of medians with 95\,\% bootstrap confidence intervals (CI; 4000 resamples
of both samples).

\textbf{Memory.} Two metrics, never mixed: the peak resident set size (RSS) of the whole process (GNU
\texttt{time} \%M), and an analytical array-storage model reported by the program (dense $3\cdot 8n^2$ bytes;
CSR $12\,\mathrm{nnz}+8(n+1)$ bytes per matrix plus the $12n$-byte accumulator).

\textbf{Order, lock and budgets.} Each configuration runs under a machine-wide lock
(\texttt{run\_measured.py}) so that benchmarks of different assignments never overlap; the method order is
shuffled per size with a fixed seed; the 1-minute load average is recorded with every row. Budgets agreed
before the full run: at most \SI{600}{s} per process (exceeding it is recorded as a \emph{timeout}), at most
8\,GiB of address space per process, enforced with \texttt{prlimit} (an allocation failure is recorded as
\emph{oom}), and at most 90 minutes of total machine time. Part~A uses
$n\in\{256,512,768,1024,1536,2048,3072,4096\}$; a method stops escalating after its first failure.
Block-size rule (declared before running): $b\in\{16,32,48,64,96,128,256\}$ is swept at $n=1024$ and
$n=2048$, and the fastest median at $n=2048$ is used for every other dense measurement.

% ------------------------------------------------------------------ Discussion
\section{Discussion}
\label{sec:discussion}
\textbf{RQ-A: effect of the dense optimisations.} On this machine both optimisations reduce the runtime at
every tested size, and the benefit grows with $n$: \val{SpMinIkj}--\val{SpMaxIkj}$\times$ for loop reordering
and \val{SpMinBlk}--\val{SpMaxBlk}$\times$ for reordering plus blocking, relative to the naive baseline. H1
is supported. The baseline's throughput collapses once its working set leaves the caches (exponent
\val{ExpNaive} instead of 3), which is consistent with its strided access to $B$: each multiply-add uses one
8-byte element of a different 64-byte cache line. Up to $n=1024$ the baseline is still 2.2--2.6$\times$
slower than \texttt{reorder\_ikj}; since none of the kernels is vectorised (\cref{sec:impl}), a plausible
explanation, not verified here, is that the baseline's single scalar accumulator forms a chain of dependent
floating-point additions, whereas the i-k-j updates of different $C_{ij}$ are independent.

\textbf{Separating reordering from blocking (H2).} Two effects must be distinguished. First, blocked is
already \val{SpBlkVsIkjTwoFiveSix}$\times$ faster than reordered at $n=256$, where $b=\val{BestBs}=n$ means a
single tile and the two kernels execute the same iteration order; this part of the gain cannot be due to
cache reuse. The compiled inner loops differ only in address arithmetic (two pointer increments vs.\ one
indexed offset); attributing the 1.2--1.3$\times$ to that difference is a conjecture that I could not test
without hardware counters. Second, the gap grows to \val{SpBlkVsIkjTwoZeroFourEight}--\val{SpBlkVsIkjFourZeroNineSix}$\times$
for $n\ge 1536$, which is exactly where \texttt{reorder\_ikj} loses about 20\,\% of its throughput while
blocked loses at most about 10\,\%. \texttt{reorder\_ikj} sweeps the whole of $B$ ($8n^2$ bytes) once per row of $C$; $B$ is
\SI{8}{MiB} at $n=1024$ and \SI{18}{MiB} at $n=1536$, i.e.\ it stops fitting in the \SI{12}{MiB} L3 between the
two sizes, whereas a $b\times b$ tile of $B$ (\SI{512}{KiB} for $b=256$) stays cache-resident. This timing is
consistent with H2 (a blocking benefit beyond the L3), but H2 as stated is only partly supported: part of the
measured benefit appears at all sizes and is not a cache effect. The block-size study agrees with Lam et
al.~\cite{lam1991} that performance is sensitive to $b$ and not monotone; here the best tested $b$ was the
largest one. Even the best kernel reaches only \val{GFMaxBlk}\,GFLOP/s, far from the
vectorised and register-blocked kernels of optimised libraries~\cite{goto2008}; the study measures the effect
of two optimisations, not the attainable peak.

\textbf{RQ-B: when does CSR help?} At $n=\val{SpN}$, CSR SpGEMM was faster than the dense kernel at every
tested density up to 50\,\% and slower from 70\,\%, for both patterns; it used less memory up to 30\,\% and
more from 50\,\%. H3 is supported, with a crossover (about \val{CrossKernelInterpUniform}\,\%) much higher than
the low-density intuition. A simple cost model explains the location: the dense kernel spends
\val{DenseNsMadd}\,ns per multiply-add for $n^3$ multiply-adds, SpGEMM about \val{NsMaddUniformDhundred}\,ns
per multiply-add for about $d^2n^3$ of them, so the predicted crossover is
$d^\ast=\sqrt{t_D/c_S}\approx\val{PredCrossUniform}\,\%$ (with $t_D$, $c_S$ the two per-operation
costs), matching the measurement. The crossover is thus set
by the ratio of the per-operation costs of the two kernels, not by the percentage of zeros alone: a faster
dense kernel (e.g.\ a vectorised library) would move it to lower densities, a slower one to higher ones.
For memory, CSR needs 12 bytes per stored entry against 8 bytes for a dense entry, and for uniform inputs
the output is full from $d\approx 5\%$; with $2\cdot 12dn^2$ bytes of inputs and $12n^2$ of output the
SpGEMM storage reaches the dense $24n^2$ at $d=50\%$, as observed. The process RSS also includes buffers
outside the timed region: the dense process holds the COO input buffers (16 bytes per nonzero) while
densifying, which explains its larger RSS at $d\ge 70\%$.

\textbf{Where indexing, conversion and output costs reduce the advantage (H4).} The evidence supports H4 and
shows three distinct costs. (i) \emph{Conversions} are irrelevant near the crossover but dominate at low
density, where they reduce a $10^4\times$ kernel advantage to about $300\times$; if the data arrive dense, the
O($n^2$) scan of dense$\to$CSR sets a floor of about 11\,ms at $n=2048$. (ii) \emph{Indexing and per-row
overheads} make each multiply-add 14\,ns at $d=0.1\%$, ten times its cost at high density; a plausible cause
is the $O(n)$ initialisation of the accumulator and the row loops, which do not shrink with $d$.
(iii) \emph{Output fill-in}: at equal multiply-add counts, the uniform pattern produces up to
\val{NnzCUoverBDtwo}$\times$ more output entries and runs up to \val{UoverBDtwo}$\times$ slower than the
banded one, and at $n=16384$, $d=1\%$ its output needs \val{ScaleRssUniformDone}\,MiB against
\val{ScaleRssBandedDone}\,MiB. The banded pattern is faster at equal density, as H4 predicts, but the gap
vanishes once its band saturates ($d\ge 50\%$). The same input density therefore gives very different costs
depending on the nonzero structure; density alone does not determine performance in these experiments.

\textbf{Optimisation vs.\ storage effects.} The two parts measure different mechanisms. In Part~A the
arithmetic is fixed ($2n^3$) and only the memory-access order changes, yielding up to
\val{SpMaxBlk}$\times$. In Part~B the sparse representation changes the amount of work itself (by $d^2$ for
uniform inputs) and the size of the output, yielding more than $10^4\times$ at $d=0.1\%$ but losing at high
density because each sparse operation is about three times more expensive than a dense one.

\subsection{Limitations}
\label{sec:limits}
All results come from one laptop (i7-9750H, gcc~13.3 \texttt{-O2}, one thread) with the \texttt{powersave}
governor and turbo enabled, so the clock frequency was not fixed; other course benchmarks were serialised by
the lock but unlocked background work existed (load average up to \val{LoadMax}). Repetitions were in-process,
so the IQR reflects within-process variability; between processes the same blocked kernel at $n=2048$ took
\val{BsBestT2048} in the block study, \val{TBlkTwoZeroFourEight} in the size sweep and \val{DenseTMin}--\val{DenseTMax}
in Part~B (different inputs, same work), i.e.\ up to 15\,\%, larger than the reported IQRs. Hardware counters
were not available (\texttt{perf\_event\_paranoid}$=4$), so cache-related explanations are inferences from timing,
sizes and throughput. For $n\ge 3072$ only $k=3$ repetitions were taken. The block-size optimum lies at the
edge of the tested grid. Only two synthetic nonzero patterns at one size ($n=\val{SpN}$) were used for the
crossover; real matrices (e.g.\ with power-law row lengths) were not tested. Strassen's algorithm, loop
unrolling and vectorisation were not studied, and the SpGEMM output columns are left unsorted, which some
consumers would require.

% ------------------------------------------------------------------ Conclusions
\section{Conclusions}
\label{sec:conclusions}
Within the tested scope (one i7-9750H core, gcc~13.3 \texttt{-O2}, float64), loop reordering and cache
blocking made dense multiplication up to \val{SpMaxIkj}$\times$ and \val{SpMaxBlk}$\times$ faster than the naive
i-j-k loop, and let both optimised kernels complete $n=4096$ within the \SI{600}{s} budget that the baseline
exceeded. The benefit grows with $n$ as the baseline becomes memory-bound; blocking adds about 1.4--1.6$\times$
over reordering once $B$ exceeds the last-level cache, plus a smaller gain at all sizes that is not explained
by cache reuse. For sparse inputs at $n=\val{SpN}$, the own CSR + Gustavson SpGEMM was faster than the best
dense kernel up to 50\,\% density and slower from 70\,\%, with a crossover near 55\,\% that a per-operation cost
model reproduces; it used less memory up to 30\,\% density. Conversions, per-row overheads and output fill-in
reduce the sparse advantage, and the nonzero pattern changes runtime and output size several-fold at equal
density. Unresolved are the hardware-level causes (no counters), the behaviour with block sizes above 256,
with real sparse matrices, and with vectorised kernels; the parallel versions of the best dense kernel are
the subject of Assignment~3.
